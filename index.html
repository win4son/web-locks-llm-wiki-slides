01 · 建立共通語言

開始前必懂的 4 個核心概念

📚 Source: WIKI-00 (index.md)

🌐 同源（Same-Origin）

指協定（Protocol）、網域（Host）與連接埠（Port）完全相同的網頁分頁。同源分頁共享同一組瀏覽器儲存空間與鎖定管理器（Lock Manager）。

⚡ 競態條件（Race Condition）

多個分頁在缺乏協調的情況下同時讀寫同一份資源，導致最終資料結果取決於不可預測的執行順序。

⚛️ 原子性（Atomicity）

一個操作要嘛全部完成，要嘛完全不執行，中間絕對不會被其他分頁插隊打斷。

✈️ 單一飛行請求（Single-Flight）

多個分頁同時需要同一份遠端資料時，僅允許一位領導分頁（Leader）實際發送請求，其餘分頁等待並共用結果。

02 · 問題痛點

為什麼「多開幾個分頁」會讓系統出錯？

📚 Source: WIKI-01 (01-multi-tab-problem.md)
💡 生活化類比：5 位沒有溝通的辦公室助理
想像辦公室裡有 5 位助理（5 個分頁），共用同一份紙本客戶名單（本地儲存）與外線電話（網路請求）。當主管說「查一下客戶最新地址」時，5 個人同時打同一支電話詢問，甚至同時拿筆塗改同一張紙，把彼此的紀錄蓋掉。

1. 重複請求與費用暴增

開啟 5 個分頁就向雲端資料庫發送 5 次相同查詢，造成 5 倍讀取計費與頻寬浪費。

2. 資料覆寫遺失（Lost Update）

分頁 A 與 B 同時讀取設定檔並修改不同欄位，後寫入的分頁會直接覆蓋先寫入的結果。

3. Token 刷新衝突

多個分頁同時拿舊的 Refresh Token 換發新憑證，觸發後端重放攻擊防護而強制登出所有分頁。

03 · 傳統解法的缺陷

為什麼 localStorage 與 BroadcastChannel 不夠用？

📚 Source: WIKI-02 (02-legacy-approaches.md)
💡 生活化類比：貼在白板上的便條紙鎖
傳統做法就像用 localStorage.setItem('lock', 'true') 在白板貼便條紙：兩位助理可能同一毫秒看到白板是空的而同時貼上去；更糟的是，如果貼便條紙的助理突然暈倒離開（分頁崩潰或強制關閉），便條紙會永遠留在白板上。
傳統協調方案 運作方式 致命技術缺陷
localStorage 標記輪詢 先 getItem() 檢查，再 setItem() 上鎖 1. 非原子性（TOCTOU 漏洞）：兩分頁同時搶到鎖
2. 殭屍鎖（Zombie Lock）：分頁當機無法自動清除鎖
BroadcastChannel API 透過訊息通道廣播「我正在抓資料」 無狀態性（Stateless）：新開的分頁收不到歷史廣播，也無法感知發送者是否已經當機

04 · 瀏覽器原生救星

Web Locks API：瀏覽器內建的智慧門禁管理員

📚 Source: WIKI-03 (03-web-locks-api.md)
💡 生活化類比：24 小時在崗的智慧門禁系統
navigator.locks 由瀏覽器核心底層統一管理排隊佇列（保證原子性）。一旦持有鎖的分頁被關閉、重新整理或當機，門禁系統感應到執行環境終止，會立即自動解鎖並交給下一位排隊者，徹底消滅殭屍鎖。

🔑 鎖的生命週期與兩種模式

  • Promise 驅動釋放：不需手動呼叫 unlock()，只要 callback 回傳的 Promise 結束（Fulfilled 或 Rejected），鎖就自動釋放。
  • exclusive（獨占鎖，預設）：同一時間僅 1 個分頁持有，適合發起唯一網路請求或寫入資料。
  • shared（共享鎖）：允許多個分頁同時讀取，但會阻擋獨占鎖進入。
// 申請名為 'sync-user-profile' 的獨占鎖 await navigator.locks.request('sync-user-profile', async (lock) => { // 同一時間全瀏覽器只有 1 個同源分頁能進入此區塊 const data = await fetchProfileFromCloud(); await saveToSharedLedger(data); // 函式結束（Promise Resolve）時，瀏覽器自動釋放鎖！ });

05 · 完整協調架構

請求帳本模式（Request Ledger）：從「排隊」進化到「共享」

📚 Source: WIKI-03 + WIKI-04

關鍵洞察（WIKI-03 & WIKI-04）：Web Locks 只負責排隊，不負責傳遞資料。若沒有搭配共享狀態帳本（Request Ledger），排在後面的 4 個分頁取得鎖後仍會各自重打 API。結合「公用登記帳本」與雙重檢查鎖定（Double-Checked Locking）即可實現真正的 Single-Flight：

STEP 1 · FAST-PATH

快速路徑檢查

先讀取本地帳本（如 localStorage），若已有未過期的有效結果，直接回傳，連鎖都不用申請。

STEP 2 · LOCK

申請獨占鎖排隊

無有效快取時，呼叫 navigator.locks.request() 排隊，選出一位 Leader 分頁。

STEP 3 · DOUBLE-CHECK

取得鎖後二次檢查

最關鍵步驟！進入鎖後再查一次帳本，若 Leader 剛寫入資料，Follower 直接讀取並結束。

STEP 4 · COMMIT

發送請求並記帳

確認仍無資料才發送網路請求，將結果與時間戳寫入帳本後自動釋放鎖。

06 · 防禦性工程設計

異常處理與死鎖預防：如果網路卡死怎麼辦？

📚 Source: WIKI-05 (05-failure-recovery.md)

即使分頁沒有崩潰，若持有鎖的 Leader 發送了一個永遠不回應的網路請求，Promise 就會永遠卡在 Pending，導致所有排隊分頁凍結。我們需要三道防禦機制：

⏱️ 1. 超時強制中斷

傳入 AbortSignal 限制排隊等待時間；並在內部對 fetch 設定 Timeout，確保 callback 內的 Promise 必定會結束並釋放鎖。

👀 2. 非阻塞試探模式

設定 { ifAvailable: true }。若鎖已被佔用，瀏覽器不排隊而直接回傳 null，適合背景定期清理或非緊急日誌同步。

🔄 3. 錯誤隔離與接力

Leader 請求失敗時不寫入空值到帳本，直接結束 Promise 釋放鎖，讓佇列中的下一個 Follower 無縫接手重試。

⚠️ 鐵則：嚴禁巢狀鎖定（Avoid Nested Locks）
切勿在持有 Lock A 的內部再去申請 Lock B，否則當另一分頁以相反順序（先 B 後 A）申請時，將造成無解的循環等待死鎖。

07 · 架構邊界與選型

什麼時候用 Web Locks？什麼時候該用 Redis？

📚 Source: WIKI-06 (06-architecture-tradeoffs.md)
💡 生活化類比：家裡的浴室門鎖 vs 全國演唱會售票系統
Web Locks API 是「家裡的浴室門鎖」，只協調同一棟房子裡的家人（同一瀏覽器的同源分頁）；Redis 分散式鎖 則是「全國售票中央資料庫鎖」，協調全台灣不同手機、不同電腦的使用者搶同一張票。
比較維度 Web Locks + Request Ledger 後端分散式鎖（如 Redis / DB Lock）
協調範圍 單一裝置、同一瀏覽器同源分頁 跨裝置（手機 + 電腦）、跨全球使用者
基礎設施成本 零成本、零外部依賴（瀏覽器原生） 需維護 Redis 叢集與網路延遲開銷
典型適用場景 避免多分頁重複查設定檔、OAuth Token 刷新 電商庫存扣減、金融轉帳、搶票系統
限制邊界 無痕視窗（Incognito）獨立隔離；不可取代後端權限驗證 不適合處理純前端 UI 重複渲染與快取協調

08 · 總結與重點回顧

建立零依賴多分頁協調系統的三個關鍵

📚 Source: WIKI-01 ~ WIKI-06

1. 捨棄手動標記鎖

不再用 localStorage 拼湊非原子鎖，改用原生 navigator.locks 獲得原子排隊與崩潰自動釋放保障（WIKI-02, WIKI-03）。

2. 鎖 + 帳本二次檢查

透過 Request Ledger 搭配 Double-Checked Locking，讓單一 Leader 抓取資料、其餘 Followers 直接複用結果（WIKI-04）。

3. 守住超時與架構邊界

加上 AbortSignal 超時防護避免請求卡死，並明確區分前端體驗最佳化與後端資料一致性邊界（WIKI-05, WIKI-06）。
